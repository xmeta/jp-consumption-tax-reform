= Machine-readable Scientific State
:revdate: 2026-09-11

== Authority

The authority order is:

. `data/scientific_state.csv` for module-level scientific state and blockers;
. `data/claim_graph.csv` and its deterministic product projections for claim-level authority;
. `STATUS.adoc` and module README files as human-facing mirrors; and
. GitHub Issues, Pull Requests, reviews, and comments as project-management/work records.

A lower item never overrides a higher one. In particular, an old Issue or PR
description is not evidence that a module is identified, causal, policy-usable,
or ready. Scientific promotion requires a repository-state change that passes the
validation gates.

The integrity gate mechanically checks that every active module declared in the
authority has its current detailed status token represented in `STATUS.adoc`.

== Active-module rule

An active research module is currently defined as a direct child directory of
`research/` that contains both:

* `README.adoc`; and
* at least one Python file.

Every discovered active module must have exactly one active row in
`data/scientific_state.csv`. A missing row, duplicate active `module_path`, or
duplicate `component_id` fails CI.

== Schema

[cols="1,3"]
|===
|Field |Meaning

|`component_id`
|Stable repository identifier for the scientific component/module.

|`module_path`
|Repository-relative active module directory.

|`display_name`
|Human-readable component name.

|`status`
|Detailed scientific-status token already used by repository status documents.

|`phase`
|Execution phase, separated from scientific identification status.

|`maturity`
|Coarse identification maturity: `NOT_IDENTIFIED`, `SENSITIVITY_ONLY`,
`PARTIALLY_IDENTIFIED`, or `READY`.

|`causal_status`
|`NOT_CAUSAL`, `DESCRIPTIVE_ONLY`, or `CAUSAL_IDENTIFIED`.

|`policy_usable`
|Whether the component is currently admissible as a direct policy-optimization
input.

|`evidence_paths`
|Semicolon-separated repository evidence paths that must exist.

|`output_paths`
|Semicolon-separated repository output paths that must exist.

|`blockers`
|Semicolon-separated unresolved conditions. Active modules below `READY` must
list at least one blocker; a `READY` component must have no unresolved blocker.

|`issue_refs`
|Semicolon-separated GitHub Issue numbers that own or document the blocker work.
Every active non-`READY` component must reference at least one Issue. Closed Issue
references are allowed when they preserve an explicit stop rule or completed
identification audit; continuing work must add the current follow-up Issue.

|`supersedes` / `superseded_by`
|Semicolon-separated component IDs for explicit scientific-state supersession.
Links must be reciprocal.

|`active`
|Whether this row participates in active-module coverage.
|===

== State transitions

The coarse maturity ladder is:

----
NOT_IDENTIFIED -> SENSITIVITY_ONLY -> PARTIALLY_IDENTIFIED -> READY
----

Promotion requires new evidence or a validated model change; it must not be
inferred from Issue/PR prose. Regression to a weaker state is allowed whenever
new evidence invalidates a stronger interpretation.

`phase` is orthogonal to this ladder. For example, a Phase-1 implementation can
be complete while its scientific maturity remains `SENSITIVITY_ONLY`.

Detailed `status` tokens remain domain-specific and may be more precise than
the coarse maturity class. The validator enforces explicit mappings for status
families whose semantics are unambiguous: sensitivity statuses map to
`SENSITIVITY_ONLY`, `NOT_READY`/`NOT_IDENTIFIED` to `NOT_IDENTIFIED`,
`ROBUSTNESS_FRONTIER` and `PARTIAL_*` to `PARTIALLY_IDENTIFIED`, and `READY*`
to `READY`.

== Semantic invariants

The repository-integrity gate consumes the machine-readable authority and
applies cross-field scientific invariants in addition to schema checks.

=== Identification state

* `policy_usable=true` requires `maturity=READY`.
* `CAUSAL_IDENTIFIED` is invalid for `NOT_IDENTIFIED` or `SENSITIVITY_ONLY`
  components.
* Every active non-`READY` component must retain an explicit blocker list.
* A `READY` component must not retain unresolved blockers.
* The structured status-family mappings above are machine-enforced.

These checks intentionally do not equate implementation phase with scientific
identification. `PHASE1_COMPLETE` can coexist with `SENSITIVITY_ONLY`.

=== Claim semantics

Paper 1's existing `paper1/data/claim_registry.csv` is used as the current
claim-level semantic registry. A claim whose `source` lies below a registered
`research/<module>` inherits that component's authority row for semantic
checks.

The gate enforces:

* `NOT_READY` claims and claims mapped to a `NOT_IDENTIFIED` component cannot
  expose a numeric headline point estimate.
* Claims mapped to `SENSITIVITY_ONLY` cannot call their allowed result an
  empirical bound, identified effect, confidence interval/region, causal bound,
  sharp identified set, or point-identified result.
* Claims mapped to a component without `CAUSAL_IDENTIFIED` cannot make an
  allowed causal-effect, causal-impact, causal-estimate, or causal-bound claim.
* Claims mapped to `policy_usable=false` cannot describe themselves as an
  optimal policy, policy optimum, optimizer input, or welfare-maximizing
  conclusion.
* High-risk vocabulary already attached to each `claim_id` in
  `forbidden_claim` cannot simultaneously appear in that claim's
  `allowed_claim`.
* An active reproduced claim cannot be supported only by
  `RECOVERY_ONLY`/`RECOVERY_GAP` evidence.

The per-claim `forbidden_claim` field is therefore used as ID-attached semantic
guard data rather than relying on the former repository-wide one-off regex.
Generalizing this registry to every research product remains a separate claim-
graph concern.

=== Failure categories

Validator diagnostics are prefixed so CI failures identify the layer that
failed:

* `schema:` -- malformed or contradictory registry structure;
* `provenance:` -- missing evidence/output paths or recovery-only active support;
* `identification:` -- impossible maturity/causal/policy/state combinations;
* `claim:` -- claim text or claim-to-component semantic contradictions.

Coverage and human-facing synchronization retain their more specific
`coverage:` and `sync:` prefixes.

== Issue/PR stale-state maintenance

Issue state is deliberately not queried from CI, so repository validation does
not depend on GitHub network availability. Instead, milestone/phase closure uses
this lightweight maintenance rule:

. inspect every `issue_refs` entry for the components changed by the milestone;
. update `data/scientific_state.csv` first when evidence changes scientific state;
. refresh materially stale active Issue bodies or close them with an explicit
  identification/stop-rule summary;
. when a blocker survives a closed Issue, add the active follow-up Issue reference
  unless the closed Issue itself records the terminal stop rule; and
. treat PR descriptions/comments only as evidence of what changed, never as the
  current scientific-status authority.

The validator enforces that active non-`READY` components have syntactically valid
Issue references. Human reconciliation of live GitHub state occurs at milestone or
phase boundaries, where it is useful and does not make scientific CI network-dependent.

== Validation

Run:

----
python scripts/test_scientific_state.py
python scripts/test_scientific_semantics.py
python scripts/validate_scientific_state.py
python scripts/reproduce.py integrity
----

The checks cover schema shape, enum values, unique primary identifiers,
conflicting active module declarations, active-module coverage, blocker
semantics, blocker-Issue reference syntax/coverage, evidence/output path existence, supersession reciprocity,
`STATUS.adoc` status-token synchronization, cross-field identification
invariants, per-claim semantic guards, and recovery-only evidence exclusion for
active reproduced claims.

A successful repository gate ends with:

----
repository scientific-state validation: OK
----

That success line therefore means the documented semantic invariants passed, not
merely that status tokens were present.
